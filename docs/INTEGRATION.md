# Integration proposal — local standards to canonical content

Date: 2026-10-09
Status: researched proposal; no schema, API, production or migration changes

## Intended destination and authority

Ryan's intended final destinations are codex-monarch/content/ranks and content/uniforms. Develop locally in this separate ranks workspace first, then transfer approved content. Images we keep/approve must be stored locally; candidate history should also remain available here.

Both intended directories are currently absent. The worker selects an explicitly configured supported type and scans only its matching folder; it does not infer new types from arbitrary directories. Current identity rules require flat <type>/<slug>.md or self-named <slug>/<slug>.md; branch-grouped ranks/navy/admiral.md would be excluded. Keep branch/category in frontmatter if retaining that layout (sync-worker/src/index.ts:67–77,119–124,373–384).

The approved monarch ADR at consolidation/decisions/001-files-as-source-of-truth.md:26 selects authoritative files and PostgreSQL as the query cache. A D1-first review/catalog stage is possible, but D1 should be a generated projection. Migrating caches must not create a second editable canon authority.

Recommendation: keep reviewed source assertions, candidate designs and approved definitions in local files; generate HTML/graphics from those records; add a D1 projection only when it has a clear serving use. Transfer approved definitions/assets to the chosen canonical content/storage ownership later. Establish a single owner for each authoritative record at that handoff.

- No dedicated rank, uniform, insignia or visual-asset type/upload API was found. Do not assume new folders create endpoint support.

### Approval boundary

Service schemas default canonical to true; worker/API upserts set is_published true (schemas.ts:167–175, write-db.ts:138–161, sync-entities.ts:127–134). Read filters do not constitute editorial approval. Adding approval_status metadata by itself will not hide a candidate.

Keep candidates outside watched canonical content until a deliberate approved promotion and serving gate exist. The PostgreSQL lore_proposals table has review fields, but corresponding proposal/review routes were not found in canon-service.

### Association and operational caveats

Admin character schemas already allow image paths, string ranks and time-bounded organization/title/rank role tables. Entity relationships and temporal roles exist in SQL, but frontmatter asset/rank references are not automatically materialized into those tables by current service writes.

Writes are disk → transactional ledger/entities → asynchronous Git persistence/webhooks. HTTP success does not prove a successful Git push. Optional If-Match exists; the current admin adapter does not send it. Authentication depends on runtime configuration; local code review is not verification of live admin.eotir.com deployment.

## Proposed record boundaries

This is a logical model for discussion, not executable DDL or an approved naming schema.

| Record | Minimum information |
|---|---|
| Source assertion | source/version/hash, sheet/gid, row/column, raw title/grade/branch, strikeout/uncertainty, observation date |
| Rank definition/version | stable identity, branch, grade family and explicit order, approved title, aliases, era/effective scope, source/ruling references |
| Tile/design system | versioned geometry, ordered palette/material tokens, master asset paths/hashes, status and approval |
| Plaque pattern | ordered rows of tile tokens, spacing/backing dimensions, design-system version, image/master references |
| Rank-pattern assignment | rank/version, exact pattern/version, branch/dress/era scope, status and explicit approval |
| Uniform standard | service/dress/era, components, wearer-side placement rules, approved rank/heraldry references, documented exceptions |
| Asset and approval history | immutable/versioned path, hash/dimensions/alpha, provenance/prompt, decision actor/date/scope, supersession |

Use composite source identity, not title alone: Navy Captain and Army Captain occupy different grades. Do not deduplicate officer roles, slash titles, shared tiers and branch ranks solely by displayed words.

Store grade order explicitly; lexical sorting does not establish hierarchy. A shared physical plaque can have multiple approved assignments, while one rank may have multiple era/dress variants. Separate pattern identity from file identity and rank identity.

For D1, normalized tables might cover branches, grades, ranks, patterns, assets, assignments and approvals, with source assertions retained. PostgreSQL can use UUIDs/JSONB while D1 uses portable text IDs/JSON text. Preserve external IDs and explicit reference maps across systems; do not reissue identities on transfer.

## Alternatives

| Route | Benefit | Cost/limitation |
|---|---|---|
| Local reviewed files, then canonical type support | Fits the user's staging-first goal and existing ADR; avoids premature DB work | Requires the later service/worker/UI extension |
| Existing entity metadata references | Smallest linkage experiment for already approved rank/image references | Weak first-class browsing/validation; rule writes currently unsupported by service |
| First-class rank/uniform/insignia types | Clear searchable identity and relationships | Coordinated enum, ledger CHECK, path maps, read/write schemas, worker, client/UI and deployment |
| Dedicated visual asset registry | Strong revision/variant/reuse support across media | More scope; should follow demonstrated requirements |

First-class support should change all affected type surfaces together. db/migrations/006_sync_ledger_ship_military_unit.sql is a precedent for a coordinated extension, not a ready-made rank migration.

The target folders need singular rank/uniform PostgreSQL enum support, plural ranks/uniforms ledger CHECK support, worker maps/TYPE_CONFIG, service read/write/required-field maps, relevant clients/UI and deployment worker instances. The systemd template configures ENTITY_TYPE per worker; deployment scripts currently do not start rank/uniform workers.

## Transfer and publication checklist for later

1. Identify exact approved definitions, assets, hashes and rulings; keep research/candidates excluded.
2. Agree canonical folder/frontmatter/type/ID conventions and local asset ownership after transfer.
3. Prepare code/schema changes and migration plan; verify staging ingestion and reference round-trips.
4. Generate the HTML/chart/projection from the same version; compare row counts and assignments.
5. Present the concrete scoped publication/transfer plan. Asset approval and production publication are distinct permissions.
6. Transfer approved bytes and content, verify local destination hashes and service/cache records, and record a receipt.
7. Preserve IDs, candidate history, rollback/supersession records and a clear authority handoff. Do not keep two editable masters.

No production D1, R2, PostgreSQL or canonical content writes were performed in discovery.
